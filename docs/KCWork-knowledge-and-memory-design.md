# KCWork 知识库与组织多人记忆设计说明

## 1. 设计目标

KCWork 的知识与记忆不是独立的文档管理系统，而是 Agent 工作时的上下文底座。它需要解决三个问题：

1. Agent 如何获得可信、及时且有权限访问的企业知识；
2. 一个系统项目如何持续积累自己的业务、代码、测试与历史需求上下文；
3. 多人协作中形成的稳定结论如何被保存、确认、复用和更新，而不是散落在聊天记录里。

因此，产品应把“管理入口”弱化，把“Agent 正在使用什么、为什么使用、引用来自哪里”放在更显著的位置。

## 2. 三层信息模型

### 2.1 企业知识库

企业知识库保存可查证、相对稳定的内容，主要包括：

- 代码 Wiki：仓库目录、代码符号、接口、依赖、调用链、ADR 和变更记录；
- 产品与业务知识：产品规范、业务术语、历史 PRD、跨系统业务规则；
- 研发与安全规范：编码、架构、安全、发布、质量门禁；
- 日常办公文档：制度、会议纪要、经营材料、方案和模板。

企业知识库不复制源系统的权限模型。检索前必须先按当前用户、项目与源文档权限过滤，回答和生成产物必须保留可点击引用。

### 2.2 项目知识

项目知识是一个长期运行系统的专属上下文，不等于简单的文件夹。它由以下内容组成：

- 项目关联的企业知识库及固定版本；
- 项目代码仓库生成的代码 Wiki；
- 已完成需求的 PRD、原型、Spec、验收结果；
- 测试基线、历史缺陷和回归范围；
- 项目自己的术语、架构说明和接口约定。

企业知识提供默认规则，项目知识负责确定“这个系统实际采用什么”。当企业知识更新时，系统先提示差异和影响范围，不直接覆盖项目已经固定的版本或项目覆盖项。

### 2.3 组织多人记忆

多人记忆保存的是经过提炼的稳定结论，而不是原始聊天记录。例如：

- 产品决策：观察者角色是否允许导出审计记录；
- 技术决策：接口需要保持几个版本周期的兼容；
- 团队约定：错误码、分支、评审和发布习惯；
- 经验事实：某类故障的常见原因和已验证处理方式；
- 企业共识：统一术语、品牌表达和合规边界。

每条记忆必须是可独立理解的原子事实，并带有范围、来源证据、贡献成员、确认状态、有效期和引用记录。

## 3. 知识与记忆的区别

| 维度 | 知识 | 记忆 |
| --- | --- | --- |
| 核心含义 | 可查证的内容 | 经协作确认的稳定结论 |
| 典型来源 | 文档、代码、需求、测试平台 | 对话、评审、实施结果、人工录入 |
| 更新方式 | 跟随源系统同步和版本变化 | 候选、确认、复核、失效 |
| Agent 使用 | 检索后按相关度引用 | 按范围直接补充约束或偏好 |
| 冲突处理 | 展示版本差异 | 新旧记忆并存并进入待复核 |
| 删除策略 | 随源权限和同步策略处理 | 删除来源不自动删除已确认记忆 |

## 4. 多人记忆生命周期

### 4.1 产生候选

Agent 可以从需求对话、代码评审、测试复盘和会议纪要中建议候选记忆，但不能自行让候选生效。候选内容要说明它为什么值得长期保存，并引用原始证据。

### 4.2 人员确认

- 项目记忆：由项目成员确认，项目管理员可以处理冲突和归档；
- 团队记忆：由团队负责人或指定维护人确认；
- 企业记忆：由企业知识管理员或对应领域负责人确认。

多人确认不是机械投票。系统应记录确认人的角色，让后续用户理解结论的责任来源。

### 4.3 生效与使用

已确认记忆按项目、团队或企业范围生效。Agent 只读取与当前任务、角色和权限相关的记忆，并在执行记录中说明使用了哪些记忆。

### 4.4 冲突与复核

新事实与旧记忆冲突时，不覆盖旧内容，而是创建待复核关系。维护人可以：

- 保留旧记忆；
- 用新结论替代并保留历史；
- 限定两个结论分别适用的系统、版本或场景；
- 将内容降级为普通知识，不再作为 Agent 的默认约束。

记忆可以设置复核周期。依赖版本、法规、组织结构或外部系统的记忆需要更短的复核周期。

## 5. Agent 上下文装配逻辑

KCWork 不应把整个知识库一次性塞进上下文。每次 Agent 工作使用以下装配顺序：

1. 确定当前用户、项目、需求和 Agent 角色；
2. 按源系统权限和项目边界过滤可访问内容；
3. 自动加入当前需求的 PRD、原型、Spec、验收标准；
4. 根据 Agent 角色检索相关项目知识；
5. 补充当前范围内已确认的项目、团队和企业记忆；
6. 对内容去重、排序并控制上下文预算；
7. 在回答、代码、文档和测试产物中保留引用；
8. 把本轮使用记录写入任务上下文，但不自动生成新记忆。

不同 Agent 的默认装配应不同：

- 产品设计 Agent：产品规范、历史 PRD、业务术语、已确认产品决策；
- 前端开发 Agent：原型、Spec、前端代码 Wiki、设计系统、前端约定；
- 后端开发 Agent：Spec、接口与数据模型 Wiki、架构规范、技术决策；
- 测试 Agent：验收标准、测试基线、历史缺陷、风险记忆；
- 日常办公 Agent：用户有权限的办公文档、会议材料、个人或团队模板。

## 6. 企业知识库管理设计

### 6.1 知识库列表

每个知识库卡片展示：类型、同步来源、负责人、内容规模、索引健康度、权限范围和最近同步时间。用户点击后查看详情，不在列表直接堆叠管理字段。

### 6.2 代码 Wiki

代码 Wiki 不是把 README 导入向量库，而是建立结构化代码视图：

- 仓库、分支、目录和模块；
- 类、函数、接口、数据模型和配置；
- 定义与引用关系；
- 服务调用和依赖图；
- PR、提交、Issue 与代码的关联；
- ADR 和关键技术决策；
- 增量索引状态及失败记录。

Agent 回答代码问题时优先引用符号级位置，并注明分支和最近索引时间。代码修改场景还要将 Wiki 结论与实时工作区代码进行校验，避免索引延迟导致错误修改。

### 6.3 日常文档知识库

日常文档知识库按照源目录授权，不鼓励管理员把所有办公文档开放给所有人。同步策略需要支持：

- 只同步已发布文档；
- 草稿仅对原有协作者可见；
- 保留标题、作者、更新时间、目录和原链接；
- 表格、附件和图片保留内容类型；
- 文档删除、移动和权限变化及时反映到索引。

### 6.4 检索与质量治理

管理者需要看到检索失败、无引用回答、陈旧内容、重复内容和权限拒绝等质量信号，而不是只看到“同步成功”。知识库健康度至少包括：同步完整度、索引新鲜度、引用可达率、无答案率和用户纠错率。

## 7. 项目知识与记忆页面设计

项目入口名称为“项目知识与记忆”，内部保留三个轻量视图：

1. 项目知识：查看项目关联的企业知识、代码 Wiki、测试基线和历史需求；
2. 多人记忆：查看已确认、待复核和候选记忆，支持共同确认；
3. Agent 上下文：解释不同 Agent 本次自动包含和主动排除了什么。

该页面不承担需求流转或项目计划管理。它的核心任务是帮助项目成员理解并校正 Agent 的上下文边界。

## 8. 权限原则

- 项目成员可以查看项目内全部需求、代码、测试和项目记忆；
- 项目角色只控制编辑、确认、归档和知识源维护能力；
- 企业知识继续继承源系统权限，加入项目不能扩大原始权限；
- Agent 的访问权限不得高于发起任务的用户；
- 所有知识引用、记忆确认、失效和覆盖操作都要记录审计日志；
- 个人记忆与组织多人记忆分离，个人偏好不会未经授权进入项目或企业范围。

## 9. 本次 Demo 覆盖范围

本次前端 Demo 已体现：

- 智能资产中的企业知识库总览、代码 Wiki、业务/研发/办公知识库；
- 知识库详情、同步状态、权限、Agent 使用规则和带引用检索示例；
- 项目、团队、企业三级多人记忆及候选确认交互；
- 项目知识、多人记忆和 Agent 上下文装配三个视图；
- 企业知识与项目覆盖关系；
- 候选记忆不自动进入 Agent、确认后才生效的治理逻辑。

Demo 暂不实现真实后端同步、权限校验、向量检索和审计存储，交互结果仅保留在当前浏览器会话中。
